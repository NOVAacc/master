# BOSH — контрольный выпуск PR #31

**Статус:** технический чек-лист. Не является разрешением на публикацию.

## Разделение изменений

- **Основная совместимость:** новые поля статусов, связка с CRM, сохранение существующих индивидуальных записей.
- **Новые функции:** клиентские защищённые ссылки, групповое расписание, участники, отдельные ссылки на услуги.
- **Отключённый функционал:** автоматический отправитель WhatsApp-напоминаний, платежи, команды сотрудников, роли и филиалы.
- **Данные:** таблицы master_clients, master_reminders, master_group_sessions, master_group_participants и новые nullable/счётчики на master_appointments.

## До развертывания

1. Зафиксировать Git SHA проверенного PR, зелёные Actions на **том же SHA**, состав миграций и текущий production SHA. Не развертывать при несовпадении.
2. Снять проверенную резервную копию production MySQL и проверить процедуру восстановления на отдельной БД. Не публиковать дампы, номера клиентов и секреты в CI.
3. Снять копию текущего кода и `.env`; убедиться, что значения APP_KEY и приватные API-токены сохраняются между релизами.
4. На **стейджинге с обезличенной копией** production проверить `php artisan migrate --pretend`, выполнить `php artisan migrate --force` и `php artisan bosh:audit-bookings`.
5. Проверить `php artisan bosh:backfill-clients --dry-run`: записать число найденных и отклонённых строк. Исторический backfill запускать отдельно **после** согласования результатов и проверки совпадения клиентов; не в составе schema migration.
6. Провести ручные сценарии клиента, мастера, групп, ссылок на услуги, уведомлений с тестовым телефоном, сравнить количество существующих записей и финансовые поля до/после миграций.
7. Проверить GitHub workflow с изолированной MySQL 5.7: PHP, TypeScript, React, миграции up/down/up, целостность.
8. Дополнительно проверить две независимые одновременные заявки на последнее групповое место, таймауты/повторные POST и отказ без второго снятия/удвоения счётчика. CI последовательных HTTP-тестов недостаточно.

## Порядок публикации при одобрении

1. Открыть согласованное короткое окно обслуживания и остановить фоновые операции, которые могут менять бронирования.
2. Ещё раз снять согласованную резервную копию БД, подтвердить возможность восстановления.
3. Опубликовать **только проверенный SHA** кода и vendor/build ресурсы. Не менять production secrets и APP_KEY.
4. Выполнить `php artisan migrate --force` один раз с логированием, после чего очистить/воссоздать штатные кеши в рамках действующей схемы хостинга.
5. Проверить доступность сайта, регистрацию, вход, кабинет, календарь, обычную запись, защищённую ссылку, отмену, групповой набор, запись группы, CRM и `php artisan bosh:audit-bookings`.
6. Включать внешние WhatsApp-напоминания только отдельным релизом с утверждённым шаблоном и журналом доставки.
7. Не запускать `bosh:backfill-clients` автоматически во время выкладки: сначала отдельно согласовать результаты dry-run.

## Откат

**Быстрый программный откат**: остановить изменения бронирований, вернуть предыдущий SHA кода и фронтенд-сборку, сохранить полную БД без разрушительных обратных миграций. Новые таблицы при этом могут оставаться: это предпочтительнее потери записей.

**Откат схемы**: `php artisan migrate:rollback` на production **не запускать автоматически**: откат новой таблицы групповых участников или клиентской CRM удалит реальные данные. Возможен только по утверждённому сценарию восстановления снимка БД, с учётом новых записей между snapshot и сбоем.

После отката проверить общий счётчик полисов/записей (если применимо), собственно записи, часы, вход и корректность URL; зафиксировать инцидент.
